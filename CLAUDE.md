# CLAUDE.md — Rules for Claude Code in SnapCrop project

> Этот файл — инструкции для AI-агента (Claude Code, Cursor agent, и т.п.).
> Агент читает его при старте работы и следует правилам в каждой сессии.
> Пользователь — не программист. Все ответы и пояснения — на русском, простыми словами.

---

## 1. О проекте

**SnapCrop** — Chrome-расширение (Manifest V3) для захвата области экрана, аннотации и сохранения в PNG/PDF.

**Стек:** Vanilla JavaScript (ES2022) · без build-шага · jsPDF (UMD) для PDF.

**Полное описание — в файле `SPEC.md`** в корне проекта. Это главный документ.

---

## 2. Источник правды

**`SPEC.md` — единственный источник правды о том, как должен работать продукт.**

- Перед началом любой задачи — прочитай релевантный раздел `SPEC.md`.
- Если ответ на вопрос есть в `SPEC.md` — следуй ему буквально.
- Если ответа нет — **остановись и спроси пользователя**. Не придумывай решение сам.
- Если у тебя есть мнение, что в `SPEC.md` ошибка или его стоит изменить — скажи это явно, обоснуй, и **жди подтверждения пользователя** перед любым отступлением от спеки.

---

## 3. Как общаться с пользователем

Пользователь не умеет читать код. Это меняет всё.

- **Объясняй простыми словами**, без жаргона. Если используешь технический термин — расшифровывай в скобках.
- **Не показывай код в чате**, если не просят. Просто работай с файлами и сообщай результат словами.
- **Никогда не говори "готово"** без чек-листа проверки. См. раздел 7.
- **На любой сложный момент** — сначала спроси, как поступить, потом делай. Не предполагай.
- **Если что-то идёт не так** — честно скажи "не получилось, давай откатимся", а не пытайся скрыть проблему ещё одной правкой.

---

## 4. Размер шагов

Работаем **очень маленькими шагами**. Каждый шаг — это:

- Одна конкретная вещь, которую можно проверить руками за 10 секунд.
- Один или несколько связанных файлов (но не "переделай всё").
- Один коммит в git в конце.

Если задача от пользователя слишком крупная — **сам раздели её на подшаги** и предложи план. Не бросайся в реализацию.

**Фазы реализации указаны в `SPEC.md` §13.** Не забегай вперёд: пока Phase 1 не работает руками, не начинай Phase 2.

---

## 5. Что НЕЛЬЗЯ делать

Жёсткие запреты — даже если кажется, что "так лучше":

- ❌ **Не добавляй фреймворки** (React, Vue, Svelte, jQuery и т.п.). Только vanilla JS.
- ❌ **Не добавляй build-шаг** (webpack, vite, rollup, esbuild). Никаких bundler'ов.
- ❌ **Не добавляй npm-зависимости в расширение.** Единственная внешняя библиотека — `jsPDF` (локальная копия в `lib/`).
  - Исключение: `scripts/generate-icons.js` генерирует иконки один раз перед публикацией. Скрипт написан на чистом Node.js (без npm-зависимостей) и **не попадает** в расширение.
- ❌ **Не создавай новых файлов** вне структуры из `SPEC.md` §2 без согласования.
- ❌ **Не меняй message protocol** (`SPEC.md` §3.3) — это контракт между service-worker и content script.
- ❌ **Не меняй формат имени файла** (`snapcrop_YYYY-MM-DD_NNN.png/pdf`).
- ❌ **Не добавляй телеметрию, аналитику, трекеры, внешние сетевые запросы.** Расширение полностью оффлайн (кроме captureVisibleTab API).
- ❌ **Не делай рефакторинг "по своей инициативе"**, если пользователь об этом не просил.
- ❌ **Не трогай файлы, не относящиеся к текущей задаче**. Если нужно — спроси.
- ❌ **Не используй TypeScript, JSX, SCSS** и другие языки, требующие компиляции.

## 6. Что обязательно делать

- ✅ **Начинай каждую сессию с короткой проверки**: какой раздел `SPEC.md` сейчас актуален, какая фаза, что было сделано в прошлый раз — спроси пользователя напрямую.
- ✅ **Перед изменением файла** — покажи список файлов, которые ты собираешься тронуть, и спроси подтверждение.
- ✅ **После изменения** — покажи краткое резюме: какие файлы изменил, что добавил, что удалил.
- ✅ **Используй plan mode** (если доступен в инструменте) для любой задачи сложнее одной строки.
- ✅ **Соблюдай структуру файлов** из `SPEC.md` §2 буквально.
- ✅ **Сохраняй CSS isolation** (`all: initial` для корневых элементов overlay) — см. `SPEC.md` §9.
- ✅ **Соблюдай границы между файлами** content-скриптов: `selection.js` — только выделение, `editor.js` — только UI редактора, `annotations.js` — только движок рисования, `exporter.js` — только экспорт, `index.js` — точка входа и координация. Не переноси логику между файлами без причины.

## 7. Чек-лист после каждой задачи

**После любого изменения кода обязательно выдай чек-лист проверки.** Формат:

```
## Как проверить

1. Открой `chrome://extensions`, нажми кнопку перезагрузки на карточке SnapCrop.
2. Открой любую обычную страницу (например, google.com).
3. Нажми Alt+Shift+S.
   ✓ Ожидаемо: страница затемняется, курсор становится crosshair.
4. Нажми ЛКМ и протащи мышь.
   ✓ Ожидаемо: рисуется прямоугольник, в углу показаны размеры в пикселях.
5. Отпусти ЛКМ.
   ✓ Ожидаемо: появляется редактор с захваченной областью.
```

Каждый пункт — **конкретное действие** + **что должно произойти**. Не "проверь, что всё работает".

Если что-то не работает — пользователь скажет конкретный шаг и симптом. Тогда:

1. Попроси открыть DevTools (F12) → вкладка Console.
2. Попроси скопировать красные сообщения оттуда.
3. По ним диагностируй проблему.

## 8. Работа с git

Пользователь использует **GitHub Desktop** (графический интерфейс), не командную строку.

- **После каждого успешного шага** напоминай: "Сейчас хороший момент для коммита в GitHub Desktop. Сообщение коммита: `<...>`".
- **Если задача провалилась 2-3 раза подряд** — предложи откатиться к последнему рабочему коммиту через GitHub Desktop (кнопка Discard changes или Revert на коммите).
- **Не пытайся выполнять git-команды в терминале** без явного запроса пользователя.

## 9. Опасные места — повышенная осторожность

В этих местах ошибиться легко, последствия плохо видны без тестов. Действуй медленно, советуйся:

- **Double-rAF перед `captureVisibleTab`** (`SPEC.md` §6.1) — overlay должен быть скрыт в момент снимка. Тестируй на разных сайтах.
- **devicePixelRatio для Retina** (`SPEC.md` §3.4) — координаты bounds в CSS px, captureVisibleTab возвращает физические px.
- **CSS isolation `all: initial`** (`SPEC.md` §9) — overlay не должен ломаться на сайтах с агрессивным CSS (Tailwind, Notion, Bootstrap).
- **Cleanup при `beforeunload`** (`SPEC.md` §10) — все DOM-элементы и слушатели должны удаляться.
- **Edge cases страниц `chrome://`, `edge://`** (`SPEC.md` §10) — `scripting.executeScript` бросает исключение, ловится в SW.

Если в одном из этих мест что-то странно себя ведёт — **не правь вслепую**. Сначала объясни пользователю, что именно происходит, потом предложи 2-3 варианта решения, дай выбрать.

## 10. Эволюция SPEC

`SPEC.md` — живой документ. Иногда придётся его менять. Процесс:

1. По ходу работы обнаружили, что в спеке пробел/ошибка/устаревшее решение.
2. **Сначала** обсуждаем с пользователем (или пользователь идёт в обычный чат и обсуждает сам).
3. Принимаем решение, фиксируем его в `SPEC.md` (в правильном разделе) и в `Decisions Log`.
4. Поднимаем версию `SPEC.md` (1.0 → 1.1 → 1.2 и т.д.) с короткой записью "что изменилось".
5. **Только после этого** — реализуем по новой спеке.

**Никогда не меняй поведение кода без обновления `SPEC.md`.** Иначе через две недели спека разойдётся с реальностью.

---

## 11. Стиль кода

- Один файл = одна понятная ответственность (как в `SPEC.md` §2).
- Внутри файла — комментарии на английском, но **короткие пояснения для пользователя** в чате — на русском.
- Имена переменных и функций — английские, понятные (`selectionBounds`, `handleMouseDown`).
- Никаких односимвольных переменных (`x`, `e`) кроме общепринятых (event handler `e`, координаты `x, y`).
- Никаких `var` — только `const` / `let`.
- Async-операции — через `async/await`, не через `.then()`-цепочки.

---

## 12. При неуверенности

**Если не знаешь, как поступить — спроси, не предполагай.**

Лучше задать пользователю один вопрос и потерять минуту, чем сделать неправильно и потерять час на откат.

Особенно это касается:
- Любого отступления от `SPEC.md`.
- Добавления чего-то нового, чего в спеке нет.
- Решений по UX (как именно должно выглядеть, где разместить кнопку и т.п.).
- Выбора между несколькими равнозначными подходами.
